# 版本管理与发布流程（1 人团队推荐）

适用范围：本仓库 `app/` 目录下的 **React + Vite（静态构建） + Express（API + 静态托管） + SQLite(better-sqlite3)** 一体应用。

目标：让你做到——**本地放心开发**、**线上可追溯**、**随时可回滚**、**发布步骤固定且不容易出错**。

---

## 0. 结论先说：你需要 Git，但不一定需要 GitHub

- **必须**：Git（本地版本管理）
- **强烈建议**：一个远程仓库（GitHub / Gitee / 腾讯云 CODING / 自建 GitLab 均可）
- **不必须**：用 GitHub 才能部署。部署可以用：
  - 服务器 `git pull` 拉代码（推荐，最省事）
  - 本地打包上传源码（你现在的方式，也可以继续用）
  - CI/CD 自动化（后期再上）

> 一人团队最常见组合：**本地 Git + 远程仓库 + 服务器拉取代码 + systemd 重启**。

---

## 1. 初始化 Git（只做一次）

在仓库根目录（包含 `app/` 和 `doc/` 的这一层）执行：

```bash
git init
git add .
git commit -m "init: baseline"
```

### 1.1 `.gitignore` 最小建议

如果你还没有 `.gitignore`，建议至少忽略：

- `app/node_modules/`
- `app/dist/`（构建产物，建议不进仓库）
- `app/database.sqlite`（真实数据不要进仓库）
- `app/database.json`（如包含真实数据也别进仓库）
- 各类日志/临时文件

> 原则：**代码进仓库，依赖和产物不进，真实数据不进**。  
> `JWT_SECRET` 等敏感配置永远只放服务器环境变量或服务器 `.env`，不要提交。

---

## 2. 建一个远程仓库（强烈建议）

任选其一即可：

- GitHub：适合开源生态、国际网络环境
- Gitee：国内更稳定
- 腾讯云 CODING：国内稳定，且后续接流水线方便

创建空仓库后，把本地推上去：

```bash
git remote add origin <你的远程仓库地址>
git branch -M main
git push -u origin main
```

---

## 3. 分支与发布约定（简单够用）

推荐：

- `main`：线上稳定版本（只放“可以上线”的代码）
- `dev`：日常开发分支

初始化 `dev`：

```bash
git checkout -b dev
git push -u origin dev
```

日常流程：

- 平时在 `dev` 开发并频繁提交
- 准备上线时，把 `dev` 合并到 `main` 再发布

---

## 4. 发布“版本号”（用 tag 锁定线上版本）

每次上线前，在 `main` 上打一个 tag（例：`v2026.04.14-1`）：

```bash
git checkout main
git pull
git tag v2026.04.14-1
git push origin v2026.04.14-1
```

好处：

- 任何一次线上版本，都有一个固定坐标
- 出问题可快速回滚到上一个 tag

---

## 5. 部署方式 A：服务器直接拉代码（推荐）

这条路线的优势：**发布时不需要手动 scp/tar**，服务器从仓库拉取固定版本。

### 5.1 服务器目录建议（避免“在代码目录里存数据”）

建议把代码与数据分开：

```text
/opt/alevelinfo/
  ├─ repo/                  # git clone 得到的源码
  ├─ data/
  │   └─ database.sqlite     # SQLite 真实数据
  └─ backup/                 # 数据库备份
```

> SQLite 数据文件建议放到 `data/`，并通过“复制/软链接/配置”让服务使用它，避免 `git pull` 时误覆盖或误提交。

### 5.2 首次在服务器拉代码

```bash
cd /opt/alevelinfo
git clone <你的仓库地址> repo
cd repo/app
npm ci
npm run build
npm rebuild better-sqlite3
```

### 5.3 日常发布（固定流程）

1) 本地：把 `dev` 合并到 `main`，打 tag 并 push（见第 4 节）

2) 服务器：切到 `main` 或指定 tag，安装/构建，重启服务：

```bash
cd /opt/alevelinfo/repo
git fetch --all --tags

# 方案 1：部署 main 最新
git checkout main
git pull

# 或 方案 2：部署某个 tag（更稳）
# git checkout v2026.04.14-1

cd app
npm ci
npm run build
npm rebuild better-sqlite3
sudo systemctl restart alevelinfo
sudo systemctl status alevelinfo --no-pager -l
```

> 说明：`better-sqlite3` 是 native 模块，**服务器侧 rebuild 很关键**（你在部署复盘里已经踩过）。

## 6. 部署方式 B：本地打包上传源码（你现在的方式，继续用也可以）

这条路线的优势：不依赖服务器装 git；缺点是每次发布要手工上传，容易漏文件。

推荐保留你现有约束：

- 不上传 `node_modules`
- 服务器端执行 `npm ci`、`npm run build`、`npm rebuild better-sqlite3`

你已经有一份可用流程，见 `doc/部署复盘-2026-04-14.md`。

---

## 7. 回滚策略（必须能“一分钟回到上个可用版本”）

### 7.1 代码回滚（用 tag）

服务器执行：

```bash
cd /opt/alevelinfo/repo
git fetch --all --tags
git checkout <上一个稳定 tag>
cd app
npm ci
npm run build
npm rebuild better-sqlite3
sudo systemctl restart alevelinfo
```

### 7.2 数据回滚（SQLite）

你至少要做到：

- 每天备份 `database.sqlite`
- 保留 7 天以上
- 能按备份恢复并启动成功

备份/恢复的基本思路见 `doc/部署指南.md` 第 8 节。

> 注意：**代码回滚 ≠ 数据回滚**。如果新版本修改了数据结构或写入了不兼容数据，回滚时要特别小心。

---

## 8. 一人团队“上线检查清单”（建议每次照着勾）

- **代码**
  - `main` 上的 commit 已推到远程
  - 已打 tag（可选但强烈建议）
- **配置**
  - 服务器 `JWT_SECRET` 未被意外更改
  - 生产环境变量齐全（端口、环境等）
- **构建**
  - 服务器 `npm ci` 成功
  - `npm run build` 成功
  - `npm rebuild better-sqlite3` 成功
- **服务**
  - `systemctl status alevelinfo` 正常
  - Nginx 仍只暴露 80/443，应用端口不对公网
- **数据**
  - 今日备份已产出
  - 你知道“上一个稳定 tag 是哪个”

## 9. 常见问题

### 9.1 我需要 GitHub 才能部署吗？

不需要。你需要的是：

- Git（版本管理）
- 任意远程仓库（备份与同步）

GitHub 只是其中一个远程托管平台。

### 9.2 我现在只有 IP 访问，没有域名，能用 HTTPS 吗？

通常不能（证书一般不为裸 IP 签发）。想要 HTTPS，建议：

- 申请域名并完成备案（服务器在大陆）
- 域名解析到服务器
- 用 certbot 配证书（见 `doc/部署指南.md` 第 6 节）
