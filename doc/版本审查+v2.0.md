# 版本审查 v2.0

　　本文档对应 **学生综合管理系统（前端展示 v2.0）** 的一次横向审查结论：覆盖 **Express 路由、SQLite 数据与后端逻辑、前端 `api.ts` 与页面、部署与配置**。审查目的不是替代专业渗透测试，而是发现 **前后端契约断裂、易 500 的边界数据、以及 SPA 部署下的典型坑**，便于版本留档与后续迭代对照。

　　**审查基准日期**：2026-04-19（与当次代码状态一致；若之后大改路由或权限，请另起新版本审查文档）。

---

## 一、审查范围与结论摘要

| 维度 | 结论 |
|------|------|
| 路由与 `api.ts` | 主要 REST 路径与 `authApi` / `studentApi` / `courseApi` / `universityApi` / `examSessionApi` 一致；学生列表类「固定路径先于 `/:id`」注册顺序正确。 |
| 数据库与逻辑 | 角色迁移与 `supervisor` 扩展与运行时代码一致；需警惕 **孤儿选课**（学生已删、选课行仍在）等历史脏数据。 |
| 前端与 UI | `MainLayout` 路由、学生只读 Tab、管理员账号页等与后端权限设计整体对齐；个别 **失败回退跳转** 仍可优化体验。 |
| 部署 | 开发态 Vite 代理 `/api` 与生产同源 `/api` 假设清晰；子路径部署需单独验证。 |

　　**当次已合入的代码向修复**（若你拉取的是此后版本，应已包含）：

1. **`GET /courses/:id/detail`**：选课关联的学生档案若缺失，不再对 `null` 解引用，避免 **500**。  
2. **未匹配的 `/api/*`**：在子路由之后增加统一 **JSON 404**，避免未匹配的 `GET /api/...` 落到 **`index.html`**，导致前端把 HTML 当 JSON 解析。

## 二、路由与前后端匹配（明细）

### 2.1 `/api/auth/*`

　　与 `authApi` 一致。管理员拉取用户列表为 **`{ users, securityNote }`** 结构，与 `AdminAccountsPage` 消费方式一致。

### 2.2 `/api/students/*`

　　`studentApi` 与各 `router.get/post/...` 路径一致。`grade-overview`、`workbench` 等 **字面路径** 注册在 **`/:id` 之前**，不会出现「把 `workbench` 当成学生 id」的拦截错误。

### 2.3 `/api/courses/*`

　　`courseApi` 与 `clone-grade`、`unit-grades`、`:id/detail` 等路径一致。`POST /courses/clone-grade` 与 `POST /courses/:id/units` 因 **路径段数不同**，不会互相误匹配。

### 2.4 `/api/universities/*`

　　`universityApi` 与后端一致。**边界说明**：若误访问 **`GET /api/universities/student`**（缺少后续 `/:studentId`），会被 **`GET /:id`** 理解为 `id = "student"` 的院校查询，通常 **404**，属误用而非主流程。

### 2.5 `/api/exam-sessions/*`

　　`examSessionApi` 与 `plans`、`overview`、`batch` 等一致。`DELETE /:id` 与 `student/...` 路径 **不会** 因顺序产生冲突（路径形态不同）。

## 三、数据库与后端逻辑

　　- **角色与 CHECK**：新建库与迁移路径应对 `admin` / `staff` / `supervisor` / `student` 与业务中间件一致。  
　　- **学生账号生命周期**：创建学生时写 `users`、删除学生时删绑定用户，与「教务管学籍、系统管登录」的设计一致。  
　　- **脏数据**：除已修复的 **孤儿选课 → 课程详情** 外，其他接口若发现类似「外键未在 DB 层强制」的关联，仍建议 **定期 SQL 巡检** 或后台小工具清理。

---

## 四、前端与 UI

　　- **路由守卫**：未登录进 `MainLayout` 会重定向登录；学生访问管理类路径在 `MainLayout` 中有重定向；管理员 `/admin/accounts` 有角色判断。  
　　- **学生只读范围**：`StudentDetail` 对学生账号限制 Tab 与 URL `?tab=` 回退，与后端「学生无写权限」互补。  
　　- **体验类**：成绩单页加载失败时按钮跳 **`/students`**，学生账号下可能更期望回本人仪表盘；属 **体验优化项**，不影响权限安全。

---

## 五、部署与配置

　　- **开发**：`vite.config.ts` 将 `/api` 代理到本机 `3001`，与浏览器请求同源代理习惯一致。  
　　- **生产**：若前端与 API 同源，依赖反向代理把 **`/api` 指到 Node**；若非同源，需配置 **`VITE_API_URL`** 与 **CORS / `CORS_ORIGIN`**，与 `app/server/index.js` 中逻辑一致。  
　　- **`vite` `base: './'`**：利于相对路径资源加载；若部署在 **子路径**（如 `https://school.edu/app/`），需在真实环境验证 **资源路径与路由 basename**。

## 六、后续关注事项（展开说明）

　　以下条目在审查中 **未全部产品化实现**，但对安全、稳定与运维成本影响较大，建议按优先级排入 backlog，并在下一版审查文档中勾选落实状态。

### 6.1 统一初始密码与口令策略（安全与合规）

　　当前学生账号默认初始密码由服务端配置（默认 `xfa19852026`，可通过环境变量 **`DEFAULT_STUDENT_INITIAL_PASSWORD`** 覆盖），入库前仍经 **bcrypt**。这意味着：

- **仍是共享秘密**：同一规则下多名新生可能短期使用同一初始串（直到各自修改密码），泄露面是「知道规则的人」而非单用户。  
- **与合规的关系**：若上级要求「不可存在默认弱口令清单」或需满足等保条款，应评估改为 **每人随机初始密码**（创建时仅弹窗/导出一次）或 **首次登录强制改密**（需前后端联调状态字段或登录后拦截页）。  
- **运维建议**：初始串变更时，除改环境变量外，应在 **校内通知** 中写清新旧生效边界（仅新建账号 vs 需批量重置旧账号），避免教务与家长口径不一致。

### 6.2 未匹配 API 的返回形态（可观测性与排错）

　　已对 **未命中任何子路由且路径以 `/api` 开头** 的请求返回 **JSON 404**（在静态页与 SPA fallback 之前），避免浏览器把 **HTML 错误页** 当成 JSON 解析。仍需知晓：

- **HTTP 方法差异**：不同客户端对 `POST`/`PUT` 等到错误路径时，默认 404 体可能是 Express 默认页；若你希望 **所有方法** 在 `/api` 下未匹配时均为 JSON，可再评估是否增加 **`app.all('/api/*', ...)`** 等（注意与现有路由的优先级，避免吞掉合法预检请求）。  
- **排错习惯**：前端 `Network` 面板中若见 **404 + `Content-Type: application/json`**，应优先怀疑 **路径或方法写错**；若见 **200 + HTML**，才怀疑是否仍走错 fallback（一般不应再出现于 `/api` GET）。

### 6.3 自动化测试与回归（质量成本）

　　当前仓库以 **人工审查 + 本地构建** 为主，缺少覆盖关键链路的 **自动化 E2E / 契约测试**。随着角色与权限变多，建议至少择要覆盖：

- 登录与各角色 **首屏可访问路由**；  
- **教务**：创建学生 → 弹窗凭据 → 学生登录；  
- **指导老师**：院校库写入与学生维度写入的 **403/200 边界**；  
- **管理员**：账号列表、重置密码、改角色。

　　测试不必一次上齐；可先 **脚本化 API**（如 `supertest`）再补少量 Playwright。

### 6.4 子路径部署与静态资源（发布形态）

　　若未来从「根路径部署」改为「子路径部署」，需同时核对：**Vite `base`**、**React Router `basename`**、**反向代理是否剥离前缀**、以及 **Open Graph / 打印页** 等是否仍指向正确绝对路径。此类问题 **在根路径环境无法暴露**，必须在目标形态下做一次 **冒烟清单**（登录、刷新深链、下载成绩单）。

### 6.5 数据质量与孤儿记录（长期维护）

　　除 **孤儿选课** 外，历史上还可能存在：重复绑定、已删用户残留外键引用（若未在 SQLite 层建 FK）、或导入数据时的 **半套记录**。建议：

- **季度或学期初**：跑一轮只读 SQL 报表（无学生姓名的选课行、无绑定的学生用户等）；  
- **删除学生**：保持当前「先删用户再删学生」的顺序，并在文档中写明 **禁止手工只删 `students` 一行** 的操作规范，减少脏数据产生。

### 6.6 审计与留痕（可选增强）

　　若校内制度要求 **谁重置了谁密码、谁改了角色** 可查询，需在后续版本增加 **审计表** 或 **结构化日志**（注意脱敏与留存周期）。当前实现以功能可用为主，**未内置审计表**。
