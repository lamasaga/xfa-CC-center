# 安全与账号机制科普（面向使用者）

　　本文说明本系统中若干「安全相关」设置**在做什么**、**为什么要这样做**，以及**学生登录名自动生成**可能遇到的情况与建议。阅读后不必成为安全专家，但能判断「哪些是正常现象」「何时需要人工介入」。

---

## 一、密码为什么「存进去就再也看不见原文」？

　　系统里保存的不是「123456」这种明文，而是经过 **bcrypt** 等算法算出来的一长串**摘要**（哈希）。特点是：

- **单向**：从摘要几乎不可能反推出原始密码（这是数学与工程上的设计目标）。
- **同一口令每次哈希可能不同**（因为会带「盐」），所以库里两行哈希即使对应同一口令，字符串也不一定一样。

　　**目的**：一旦数据库泄露（备份盘丢失、服务器被入侵等），攻击者拿到的是哈希，而不是全校师生的明文口令，损失面会小很多。

　　**对你操作的影响**：管理员在「账号与权限」里**不能真正「查看」某人当前正在用的密码原文**——不是不想做，而是技术上没有存。能做的是：**重置为新密码**，再通过**线下或可信渠道**把新口令告诉对方。

---

## 二、登录接口为什么要「限流」？

　　系统在 `/api/auth/login` 上对「同一来源在短时间内尝试登录的次数」做了限制（例如每 5 分钟、同一 IP + 用户名组合最多若干次）。

　　**目的**：减缓**暴力猜密码**（不断试密码）和**撞库**（用别处泄露的密码表来试）的速度。不是防住一切攻击，而是提高成本、减少误伤（正常输错几次一般不会触发）。

　　**对你操作的影响**：若多人共用出口 IP（例如同一校园网），又都在短时间内反复试错密码，可能更容易碰到限制；稍等几分钟或确认用户名无误即可。

## 三、HTTP 响应里的那些「安全头」是什么？

　　例如：`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer` 等。

　　**通俗理解**：告诉浏览器「别乱猜内容类型」「尽量别被嵌进陌生网站的框架里做点击劫持」「少往外带来源地址」等，降低一些常见**浏览器侧**攻击的成功率。

　　**目的**：在「应用自己写得没问题」之外，多一层**默认防护**。它们不替代 HTTPS，也不替代权限校验。

---

## 四、登录后用的 JWT 为什么还要「每次请求再去数据库核对用户」？

　　JWT 像一张**短期内可信的通行证**，里面带了用户 id、角色等。若只在登录时写进 token、之后**永远信任 token 里的角色**，会出现问题：例如管理员在库里已经把某人「降级」或删号，旧 token 在过期前仍可能被滥用。

　　本系统在校验 JWT 后，会**再读一次数据库**里的用户与角色（并与学生绑定关系等一致）。

　　**目的**：让**权限变更、删号**能较快生效，减少「旧 token 绕过新权限」的风险。

　　**对你操作的影响**：token 有过期时间（例如 24 小时），到期需重新登录，这是正常现象。

---

## 五、生产环境常听到的「HTTPS」和「JWT_SECRET」和你有什么关系？

　　- **HTTPS**：浏览器到服务器之间的传输加密。没有它，同一 WiFi 下的旁听者更容易看到请求内容（包括登录过程若设计不当会更危险）。**上线对外服务时强烈建议全程 HTTPS。**
　　- **JWT_SECRET**：用来签发/校验 JWT 的密钥。若泄露，攻击者可能伪造任意用户的 token。**生产环境必须用足够长、随机的密钥，且只放在环境变量等保密位置，不要写进代码仓库。**

　　这两项多半是**部署与运维**时配置，但理解其目的有助于你参与验收或和运维沟通。

---

## 六、权限分角色（管理员 / 教务 / 指导老师 / 学生）的意义

　　**目的**是「**最小权限**」：每个人默认只能做本职工作需要的操作，减少误操作和内部滥用面。

　　- **学生**：以浏览与下载成绩单等为主，敏感写操作在后端直接拒绝。
　　- **教务**：负责学生档案的创建与删除（并联动学生账号），以及日常教学数据维护。
　　- **指导老师**：侧重院校库与升学相关维护，但不经手「新建/删除学生档案」这一环（与职责划分一致）。
　　- **管理员**：账号与角色、重置密码等全局能力。

　　**注意**：前端隐藏按钮只是体验；**真正生效的是后端接口校验**。这样即使有人改网页或伪造请求，也越权不了。

## 七、学生登录名自动生成：会不会出错？边界在哪里？

　　当前规则（简化理解）：**英文（小写、去空格） + 中文姓名（小写、去空格） + 入学年份后两位**；初始密码默认为 **`xfa19852026`**（可由环境变量 `DEFAULT_STUDENT_INITIAL_PASSWORD` 覆盖；入库前同样经 bcrypt）。

### 7.1 系统在「防重名」上做了什么

　　用户名在数据库里要求**唯一**。若按规则拼出来的字符串已经存在，程序会自动在末尾加 **`1`、`2`、…** 直到找到一个未占用的用户名。

　　因此：**一般不会因为重名而导致创建失败**；但教务在弹窗里看到的最终用户名，可能与「心里预期的纯规则字符串」差一个后缀数字，这是**有意设计**，不是 bug。

### 7.2 仍建议你留意的「人为与数据质量」问题

　　- **英文姓名必填且建议规范**：规则依赖英文段；若教务漏填，系统会拒绝创建（避免生成无意义账号）。
　　- **中文名、英文名里的空格与大小写**：会自动去掉空格、英文转小写；**中文没有大小写概念**，原样保留字符。若同一届有两个学生「中文名 + 英文名」在规则下完全一样，会出现**自动加数字后缀**区分——需要教务心里知道「为什么多了一个 1」。
　　- **特殊符号与表情**：若姓名里含有特殊符号，会原样进入用户名（经过去空格、英文小写处理）。极少数符号可能在某些输入法或旧系统里显示异常；**建议姓名以常规汉字与字母为主**。
　　- **改名后用户名是否跟着变**：当前实现是**创建时定死用户名**；学生后来改了档案里的中英文姓名，**登录名默认不会自动跟着改**（避免与已有账号冲突、也避免误改导致全员无法登录）。若改名后希望登录名也更新，需要**管理员侧策略**（例如重置/新建绑定——属于后续可增强流程）。
　　- **长度**：数据库对 `username` 长度若有限制，极长的姓名组合理论上可能超长（视库表定义而定）；日常学校场景极少见。若担心，可在教务录入规范里限制姓名展示长度。
　　- **统一初始密码**：便于开学统一发放，但仍属**共享秘密**，不宜对外公开文档长期张贴；适合**内网、受控环境**并应配合「首次登录改密」等制度。若对合规要求高，可用环境变量改为**随机初始密码**并由教务单独告知，或上线**强制改密**流程。

### 7.3 「能否保证永远不出错？」的诚实结论

　　可以保证的是：**在规则明确、数据合法的前提下，系统会稳定生成唯一用户名并成功入库**；不能保证的是：**业务上「这个名字是否合适、是否好记、是否与家长口头传达的一致」**——这依赖**录入规范**与**创建成功后弹窗里对用户名、初始密码的核对与告知**。

　　建议教务流程：**创建成功 → 当场把弹窗里的用户名与初始密码记入学籍表或当面交给学生 → 督促首次登录后修改密码**。

## 八、读完你可以用这几句话自查

　　1. 密码：**库里不是明文**；忘记只能**重置**，不能「查出来」。  
　　2. 登录：**限流**是为了拖慢暴力猜密码。  
　　3. 权限：**以后端为准**；角色分工减少误操作与滥用面。  
　　4. 学生账号：**规则 + 自动防重名**保证技术可创建；**好不好用、是否与口头一致**要靠录入规范与创建后的核对。

　　若你希望把某一条（例如「首次登录强制改密」「改名后同步用户名」）做成明确的产品规则，可以在需求里单独列一条，便于开发与验收对齐。
