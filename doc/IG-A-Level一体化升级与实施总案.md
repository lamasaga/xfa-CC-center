# IG–A Level 一体化升级与实施总案

> 文档状态：实施基线草案  
> 编制日期：2026-08-30  
> 适用范围：`app/` 主系统及其关联的院校探索站点  
> 重要说明：本文依据当前仓库进行只读审查，并未连接或修改线上服务器、线上数据库。涉及法律合规的内容是产品与工程控制建议，不替代专业法律意见。

## 1. 结论先行

  本次升级不应被理解为“给九年级多加一个筛选项”，而应把现有 A-Level 成绩与升学管理系统扩展为四年连续的校内学习管理系统：九年级进入 IG 阶段，十至十二年级继续进入学校既有的 A-Level 路径；学生的课程选择、教学班、教师、课表、考试报名、成绩、升学任务和风险预警沿同一条学生时间线连续保存。

  实施上建议保留现有 React、Express 和 SQLite 架构，先用增量表和受控迁移补齐领域能力，不在本次升级中同时更换技术栈或数据库。当前数据量和部署方式没有证明必须立即迁移 PostgreSQL；贸然换库会把数据风险与功能升级风险叠加。只有在实际出现持续写入竞争、跨校多租户或数据量明显超过单机能力后，再单独评估数据库迁移。

  项目的第一里程碑不是新页面，而是“可恢复”：确认线上数据库真实路径，完成一致性备份、异地副本、恢复演练和匿名化测试库。所有数据库结构变更必须在副本上演练，通过后才进入维护窗口。未满足这一条件时，不允许上线课程贯通、排课或权限迁移。

  排课首版采用“学校控制的半自动排课”：系统先根据学生选课需求形成教学班，再在教师可用时间、学生冲突、教室容量、锁定课节等硬约束下给出方案；教务可以锁定、移动、豁免并重新计算。发布前必须做到硬冲突为零。暂不为一个尚未量化的规模引入独立优化平台；若真实数据证明普通求解无法在验收时间内完成，再在同一调度接口后替换为成熟约束求解器。

## 2. 本次目标与边界

### 2.1 必须实现

- 九年级 IG 阶段进入学生、课程、成绩、考季、任务和风险视图。
- IG、IAS/AS、A Level/IAL 按考试局、资格、科目、版本和考试系列被准确区分。
- 建立只引用官方来源、带生效期和复核记录的课程考试资讯库。
- 支持学生选课申请、教务审核、教学班编组、教师与教室安排、课表发布及变更通知。
- 保留学校对开课、容量、教师可用时间、固定课节、合班与例外审批的最终控制权。
- 将现有宽泛角色权限收紧为“角色 + 操作权限 + 数据范围”，所有限制在服务端执行。
- 在不删除现有业务能力的前提下，重组导航和页面层级，减少重复入口和跨页跳转。
- 建立上线数据库的备份、迁移、校验、恢复和审计闭环。

### 2.2 本期不做

- 不把系统扩张为多学校 SaaS、多租户平台。
- 不在没有实际瓶颈证据时迁移数据库或拆分微服务。
- 不自动抓取后未经人工复核就把考试局网页内容发布为正式规则。
- 不把“系统推荐课程”变成替代学校审批或升学顾问判断的自动决定。
- 不承诺一次性覆盖所有考试局和所有科目；首批以学校真实开设的考试局、科目和考季为准。

## 3. 当前系统审查结论

### 3.1 已有能力

| 范围 | 当前实现 | 可复用部分 |
|---|---|---|
| 前端 | Vite + React + TypeScript，单页应用 | 组件库、现有学生详情、成绩、考季、院校页面 |
| 后端 | Express CommonJS API | 路由结构、身份校验中间件、API 冒烟测试 |
| 数据 | SQLite + WAL，已启用外键 | 现有学生、课程、选课、单元成绩、考季、院校数据 |
| 角色 | `admin`、`staff`、`supervisor`、`teacher`、`student` | 登录、密码哈希、学生本人数据边界 |
| 运维 | systemd 部署、构建脚本、备份说明、健康检查 | 可作为新的发布闸门基础 |
| 业务 | 学生档案、成绩、A-Level 单元、考季规划、语言成绩、任务、院校与专业 | 升级时应保留并迁移，不重做已有功能 |

### 3.2 已确认的结构问题

| 问题 | 代码证据 | 影响 |
|---|---|---|
| `students.grade` 实际混合表达“入学届”，不是当前年级 | 年级导航使用届别标签；学生表只保存一个 `grade` | 无法准确表达九至十二年级的年度变化 |
| `courses` 同时承担科目、开课和教师配置 | 表中同时存在 `subject_code`、`teacher_id`、`academic_year`、`semester` | 同一科目多班、多教师、多学期时会混乱 |
| 课程被迁移为 `grade_level='ALL'` | `db.js` 中存在统一为 `ALL` 的迁移 | 无法表达 IG/IAS/A Level 的适用阶段和先修关系 |
| 只有选课结果，没有选课流程 | `student_courses` 直接表示已选或退课 | 缺少学生志愿、审核、候补、容量和变更记录 |
| 没有排课领域数据 | 无教学班课节、时段、教室、教师可用性、课表版本表 | 无法检测教师、学生和教室冲突 |
| 权限粒度过宽 | `canModify` 允许管理员、教务、指导老师修改多类学生数据 | 不能限制到任教班级、负责学生或具体字段 |
| 教师权限与职责错位 | 教师能维护考季计划，却不能维护任教课程成绩 | 容易扩大考试规划权限，同时妨碍日常教学 |
| 会话令牌在 `localStorage` 保存 24 小时 | `AuthContext.tsx`、`api.ts` | 一旦发生脚本注入，令牌更容易被读取 |
| 生产启动仍带默认种子账号逻辑 | `db.js` 和 `config.js` | 环境配置失误时可能产生已知初始口令 |
| 运行时自动执行轻量迁移 | `db.js` 中包含多段建表、加列和数据修正 | 应用启动与数据变化耦合，难以审计和回滚 |
| 缺少操作审计和历史版本 | 当前表多数只保存最新状态 | 无法回答“谁在何时改了课表、成绩或权限” |

  上述结论是代码级审查，不等同于完整渗透测试。特别是反向代理、HTTPS、服务器权限、真实备份任务和线上环境变量只能在获得线上只读访问后另行核验。

### 3.3 仓库与应用边界收口

| 目录 | 当前判断 | 升级处理 |
|---|---|---|
| `app/` | 唯一具备后端、数据库、身份和完整业务路由的主系统 | 作为唯一业务事实源和正式登录入口 |
| `study-app/` | 独立的只读院校探索前端，构建后由主服务挂载在 `/study` | 保留为受控子应用；院校数据改由版本化导出或只读 API 提供，不复制学生敏感数据 |
| `studentapp/` | 前端展示版，含硬编码示例成绩和指向本机的链接，没有独立后端 | 不作为第二套生产系统；其中行政班、学科班、成绩单等有效需求并回 `app/`，验证等价后再由负责人决定归档 |
| 其他实验/历史目录与压缩包 | 与正式部署边界混在同一仓库 | 发布包使用明确允许清单，只包含运行所需文件；不在本次任务中擅自删除历史资产 |

  这样收口后，登录、权限、学生、课程、选课、课表和审计只有一个事实源；院校探索可以保持独立视觉体验，但不能形成第二套账号或学生数据库。共享类型和接口只有出现实际重复后再提取，不先建设通用前端平台。

## 4. 目标业务架构

### 4.1 一条连续的学生路径

| 校内阶段 | 默认年级映射 | 系统重点 | 说明 |
|---|---:|---|---|
| IG 基础/IG | 9 年级 | 学科基础、IG 路径、阶段评估、A-Level 方向探索 | 学校可配置为 IG Foundation、IG1 或加速 IG，不写死为考试局标准学制 |
| A-Level 起步 | 10 年级 | 方向确认、先修检查、课程组合、教学班 | 延续学校现行课程安排 |
| IAS/AS 或 A-Level 进阶 | 11 年级 | 模块/组件考试、重考规划、预估成绩 | 具体名称由考试局和科目规则决定 |
| A-Level 完成与申请 | 12 年级 | 最终考试、语言/附加考试、申请与去向 | 课程、考试和升学任务共用时间线 |

  “九年级 = IG”是学校的课程实施政策；“IGCSE 通常按两年设计”是考试局的资格说明。系统必须同时保存这两个事实，避免以后把校内安排误报成官方制度。年级、入学届、学年和资格阶段必须是四个不同字段。

### 4.2 角色工作台

| 用户 | 一级导航建议 | 首页只回答的问题 |
|---|---|---|
| 学生 | 今日、我的课程、选课、课表、成绩与考试、升学计划、我的资料 | 今天上什么课、下一项任务是什么、选课/考试状态如何 |
| 教师 | 今日、我的教学班、课表、成绩录入、学生支持 | 今天教什么、哪些成绩待录、哪些任教学生需要关注 |
| 指导老师 | 工作台、负责学生、学业与升学、任务、院校资讯 | 哪些负责学生有学业或申请风险 |
| 教务 | 学校总览、学生、课程与教学班、选课、排课、考试管理、报表 | 哪些资源冲突、哪些流程待审核、课程供需是否失衡 |
| 管理员 | 账号与权限、基础配置、审计、安全与运维 | 谁有高权限、系统与备份是否健康 |

  当前“成绩管理”“考季规划”等入口依赖最近查看的学生，容易让用户丢失上下文。升级后应先进入清晰的列表或工作台，再进入具体学生；学生详情内部保留个人维度的课程、成绩、考试、活动、院校和任务标签页。

## 5. 课程与考试资讯库

  资讯库不保存模糊的网页摘要，而保存可追溯的结构化事实。每条规则都必须能回答：哪个考试局、哪项资格、哪个科目代码、适用于哪个 syllabus/specification 版本、哪些考试系列、从何时生效、由谁核对、官方原文在哪里。

### 5.1 首批数据对象

| 对象 | 核心字段 |
|---|---|
| 考试局 | 名称、官方域名、中心编号配置、地区/行政区配置 |
| 资格 | IG/International GCSE/IAS/AS/A Level/IAL、评分制、典型路径 |
| 科目规范 | 科目代码、名称、资格、版本年份、生效/失效日期、官方链接 |
| 组件/单元 | 代码、名称、必选/可选、权重、计分、Core/Extended、可用考季 |
| 考试系列 | 年、系列、报名截止、准考/材料节点、考试日期、放榜日期、版本号 |
| 制度规则 | 重考、cash-in、carry forward、access arrangements、coursework、特殊考虑 |
| 来源记录 | URL、标题、发布者、发布日期、检查日期、内容哈希、复核人、状态 |

### 5.2 内容治理

- 只把考试局、监管机构或政府网站列为“官方”；培训机构和论坛只能进入“参考”，不得驱动系统规则。
- 系统保存官方链接、结构化事实和必要的内部备注，不整站复制受版权保护的材料。
- 每条规则采用生效日期，不直接覆盖历史版本；历史学生和历史考季继续引用当时版本。
- 每季度例行复核，报名季开始前和考试局发布变更后进行专项复核。
- 任何影响选课、报名或成绩计算的变更必须经过第二人复核后发布。
- 抓取或提醒可以自动化，但“变更已确认”必须由授权人员操作。

  初始官方资料、已核对事实和维护流程见 [课程考试官方资讯库基线.md](./课程考试官方资讯库基线.md)。

## 6. 数据模型增量设计

### 6.1 保留并逐步澄清现有表

  不直接重命名或删除 `students`、`courses`、`student_courses`、`course_units` 等线上表。先新增表和可空关联字段，完成数据回填和双读验证后，再停止使用含义重叠的旧字段。这是“扩展—迁移—收口”做法，可使代码回滚不依赖破坏性数据回滚。

### 6.2 建议新增的最小表组

| 表组 | 建议表 | 用途 |
|---|---|---|
| 学年阶段 | `academic_years`、`student_year_records` | 保存学生每学年的年级、资格阶段、学籍状态，保留历史 |
| 资格目录 | `qualification_specs`、`qualification_components` | 保存考试局、资格、科目版本及组件/单元规则 |
| 官方来源 | `official_sources`、`rule_revisions` | 记录官方链接、事实版本、复核和生效状态 |
| 开课 | `course_offerings`、`teaching_groups`、`teaching_group_teachers` | 把科目目录与某学年实际开课、教学班、教师分开 |
| 选课 | `course_requests`、`request_choices`、`enrollment_changes` | 保存志愿、审核、候补、录取、退改课和原因 |
| 资源 | `rooms`、`time_slots`、`teacher_availability` | 定义教室容量、设备、学校时段和教师不可用时间 |
| 排课 | `schedule_versions`、`lesson_requirements`、`scheduled_lessons`、`schedule_exceptions` | 支持草稿、锁定、冲突、发布、回滚和例外审批 |
| 安全 | `user_sessions`、`audit_events`、`schema_migrations` | 支持会话撤销、操作审计和显式迁移版本 |

### 6.3 关键约束

- 一个学生在同一学年只能有一条有效年级记录。
- 一个学生不能重复加入同一教学班；退课保留变更历史，不物理删除。
- 发布课表内，同一时段的教师、学生和教室分别只能占用一次。
- 教学班人数不得超过有效容量；超额必须有授权例外和原因。
- 课程组件、考试系列和成绩记录必须引用具体规范版本，不能只存自由文本。
- 关键业务删除改为停用或软删除；学生档案物理删除需要二次授权并先导出审计清单。

## 7. 选课与排课方案

### 7.1 选课流程

1. 教务发布学年、阶段和可选课程包，设置必修、互斥、先修、容量和志愿数量。
2. 学生查看课程说明、前置要求、潜在时间冲突提示，提交分优先级志愿。
3. 指导老师只审核其负责学生的学业合理性；教务拥有最终录取和例外权。
4. 系统按需求形成教学班建议，显示开班、合班、增班和师资缺口。
5. 教务确认教学班、主讲/协同教师、课时需求和可用教室。
6. 选课结果在课表发布后生效；所有退改课进入变更流程并保留原因。

### 7.2 排课硬约束

- 同一教师、学生或教室在同一时段不可重复占用。
- 教师不可用时段、锁定课节和学校禁排时段必须遵守。
- 教室容量和必要设备必须满足教学班要求。
- 每个教学班每周课时、连堂长度和间隔规则必须满足。
- 学生已获批课程必须全部进入可行课表；无法满足时明确列出无解原因，不静默丢课。
- 已发布考试时间视为强约束；教学课表不得覆盖校内明确禁止的考试准备时段。

### 7.3 排课软目标

- 尽量满足教师偏好，但偏好不能压过学生已批准课程。
- 减少学生与教师的零碎空档和跨教室移动。
- 避免同一学科长期集中在一天或总是安排在最后一节。
- 尽量保持同一教学班的教室稳定，并均衡教师日课时。

### 7.4 学校控制机制

| 机制 | 产品行为 |
|---|---|
| 草稿版本 | 每次计算产生新版本，不覆盖当前已发布课表 |
| 手工锁定 | 教务可锁定教师、教室或课节，重新计算时必须保持 |
| 冲突中心 | 按教师、学生、教室、容量、课时五类聚合，支持定位到具体记录 |
| 例外审批 | 只有教务或管理员可豁免软规则；硬冲突原则上不可豁免 |
| 差异预览 | 发布前显示相对当前版本的教师、学生和教室变更 |
| 双人发布 | 生成者与发布者分离；小规模学校可由管理员配置是否启用 |
| 快速回滚 | 保留上一发布版本，一次操作恢复并写审计日志 |

### 7.5 求解策略

  首版在现有后端内实现确定性的“需求分组 + 约束校验 + 启发式放置 + 局部修复”，并把硬约束写成独立、可测试的规则。真实学校数据验收时记录教学班数、时段数、求解时间和无解比例。只有在匿名化真实规模下无法达到约定时间，才把求解实现替换为 CP-SAT 等成熟约束求解器；数据表、API 和用户流程不因此变化。

## 8. 权限与安全重构

### 8.1 权限原则

  首版不建设可任意配置的“权限平台”。角色仍沿用现有五类，但服务端使用固定权限码和数据范围判断，减少散落在各路由里的角色条件。前端只负责隐藏或禁用按钮，绝不作为权限边界。

| 能力 | 管理员 | 教务 `staff` | 指导老师 `supervisor` | 教师 | 学生 |
|---|---:|---:|---:|---:|---:|
| 账号与角色管理 | 全部 | 无 | 无 | 无 | 本人改密 |
| 学生学籍增删/归档 | 审批/全部 | 负责 | 只读 | 无 | 本人只读 |
| 联系人与敏感资料 | 按需 | 按需 | 仅负责学生必要字段 | 默认不可见 | 本人可见 |
| 课程目录/开课 | 配置 | 维护 | 只读 | 任教班只读 | 已发布只读 |
| 选课审批 | 查看/例外 | 最终审批 | 负责学生建议 | 查看任教结果 | 提交本人志愿 |
| 排课 | 发布/回滚 | 生成、编辑、校验 | 查看 | 本人可用性与课表 | 本人课表 |
| 成绩 | 查看/更正审批 | 全校导入与更正 | 负责学生只读 | 仅任教班录入 | 本人只读 |
| 考试报名与规划 | 查看/例外 | 维护 | 负责学生建议 | 只读必要信息 | 本人只读 |
| 院校与升学 | 配置 | 查看 | 维护与负责学生操作 | 默认无 | 本人查看/意向 |
| 审计日志 | 全部 | 本业务范围 | 无 | 无 | 无 |

### 8.2 必做安全项

1. 将 JWT 从 `localStorage` 迁移为服务端可撤销的会话，浏览器只保存 `HttpOnly + Secure + SameSite` Cookie；状态变更请求增加 CSRF 防护和 Origin 校验。
2. 生产环境取消默认种子账号和统一学生初始口令；初始密码改为一次性随机口令，首次登录强制修改，高权限账号启用 MFA。
3. 登录限流迁移为可跨进程持久化的账户/IP 组合策略，增加失败审计、会话撤销、停用账号即时失效。
4. 所有 API 使用统一输入校验和字段白名单；所有对象访问先验证数据范围，补齐跨角色、跨学生、跨教学班的越权测试。
5. 增加内容安全策略 CSP、HSTS、代理层 HTTPS 强制、依赖漏洞检查和敏感配置扫描。
6. 学生头像改为鉴权下载或使用不可预测短期地址；上传验证文件签名、解码结果、大小和尺寸，不只检查 MIME。
7. 建立 `audit_events`：记录操作者、动作、对象、前后差异摘要、原因、时间、来源 IP/请求号；不在日志保存密码、令牌或完整敏感字段。
8. 对学生、监护人、成绩和升学数据进行分类分级，设置最短必要保存期限、导出审批、删除/更正流程和安全事件预案。

  系统会处理未成年人信息。根据《个人信息保护法》，不满十四周岁未成年人的信息属于敏感个人信息，相关处理需要监护人同意并制定专门规则。上线前应由学校确认其学生年龄、告知与同意依据、保存期限和供应商数据流向，并对相关处理开展影响评估。

## 9. 功能与体验增强

### 9.1 保留功能的重组方式

| 现有功能 | 升级后的归属 | 调整重点 |
|---|---|---|
| 学生列表/详情 | 学生中心 | 统一搜索、批量操作、四年时间线、按权限裁剪字段 |
| 成绩管理 | 教学班成绩 + 学生学业档案 | 教师按班录入，教务批量导入，修改留痕 |
| 考季规划 | 考试管理 | 区分校内课表与官方考试；绑定考试局规范版本 |
| 年级概览 | 学校总览 | 按学年、当前年级、阶段、班级切换，不再混用入学届 |
| 课程管理 | 课程与教学班 | 分开科目目录、学年开课、教学班、任教教师 |
| 院校维护/探索 | 升学中心 | 保持探索体验，官方要求与内部建议分别标注来源和日期 |
| 任务与风险 | 角色工作台 | 只显示可执行事项，风险可解释并能跳到原始记录 |

### 9.2 统一交互规则

- 列表页统一搜索、筛选、排序、批量操作和已应用筛选提示。
- 编辑使用明确的保存/取消，不在离开页面时静默提交；未保存离开需提醒。
- 删除高风险对象前展示影响范围；有历史引用时只允许停用或归档。
- 所有长任务显示进度和结果摘要；失败说明原因及修复入口，不只显示“操作失败”。
- 课表、成绩和选课使用桌面优先的高密度视图，同时提供手机端当天课表与关键任务，不强行把完整排课器塞进小屏。
- 颜色不作为唯一状态信号；表格支持键盘、焦点可见、表单标签和错误提示关联。
- 学生和教师首页控制在一屏内呈现最重要事项，低频配置进入二级页面。

### 9.3 近期功能增强清单

| 服务对象 | 本期增强 | 暂缓项与理由 |
|---|---|---|
| 学生 | 四年课程时间线、选课志愿、个人课表、成绩趋势、考试/任务提醒、成绩单下载 | 不做自动替学生决定专业或课程 |
| 教师 | 我的教学班、批量成绩录入/导入、草稿校验、本人课表、学生异常名单 | 不开放全校学生隐私和全校考试规划写权 |
| 指导老师 | 负责学生清单、IG 到 A-Level 学业路径、升学里程碑、可解释风险和跟进记录 | 不让指导老师代替教务更改学籍或正式课表 |
| 教务 | 行政班/教学班、课程供需、选课审核、师资工作量、排课冲突、考试报名清单、数据质量报告 | 首期不建设复杂薪酬和人事系统 |
| 学校管理 | 年级/阶段概览、开课与满班率、师资冲突、成绩分布、考试节点、升学进度和数据健康 | 不把相关性指标包装成自动绩效结论 |
| 成绩单 | 校内考核项目与权重、期中/期末归档、教师评语、审核、导出；外部考试成绩保持原始口径 | 不把校内加权分与考试局资格成绩混为一个分数 |

  考勤、家校消息、复杂审批和人事功能只有在学校确认现有流程与数据责任后再排入后续需求，不因它们常见就提前建设。首期先把课程、教学班、成绩、选课、课表和考试这一条主链做完整。

## 10. 数据库保护与迁移方案

### 10.1 不可跳过的上线闸门

| 闸门 | 通过标准 |
|---|---|
| 真实路径确认 | 运维从运行进程、服务环境或挂载配置确认 `SQLITE_PATH`，不凭文档猜测 |
| 一致备份 | 使用 SQLite `.backup` API/CLI，或停服后完整复制主库及 WAL 相关文件 |
| 完整性校验 | 在备份副本执行 `PRAGMA integrity_check`，结果为 `ok` |
| 恢复演练 | 在隔离目录恢复，使用当前版本启动并完成登录、查询和测试写入 |
| 异地副本 | 至少一份加密备份位于另一台主机或私有对象存储 |
| 可回滚代码 | 上一稳定构建、环境配置和依赖锁文件可用 |
| 匿名测试库 | 开发和 UAT 不直接使用含真实姓名、电话、邮箱的生产副本 |

### 10.2 建议恢复目标

- 工作时段每小时生成一致快照，夜间生成每日备份。
- 恢复点目标 RPO 不超过 1 小时；恢复时间目标 RTO 不超过 4 小时。
- 每日备份保留 30 天、每月备份保留 12 个月；具体期限由学校的数据保存制度确认。
- 每月自动校验最近备份，每季度进行人工恢复演练并留存记录。
- 备份加密、目录最小权限、下载有审计；备份不得进入 Git、应用静态目录或开发者个人网盘。

### 10.3 迁移流程

1. 给当前线上版本和数据库快照建立同一发布编号。
2. 在匿名化副本上运行只读预检：表数、行数、孤儿记录、重复关系、无效枚举和空关键字段。
3. 执行可重复、带事务、带版本号的新增表/加列迁移；生产启动只校验版本，不再自动改表。
4. 回填新结构，输出每类记录的源数量、成功数、跳过数、冲突数和校验和。
5. 新旧查询并行比对；差异必须解释，不允许靠手工直接改生产库消除。
6. 小范围开启 IG 和选课功能，观察日志与审计；排课先以草稿运行，不影响当前课表。
7. 维护窗口前再次热备，停写后做最终增量回填和完整性检查。
8. 切换读取路径并进行业务抽查；异常时回滚代码和功能开关，保留已新增数据，不执行破坏性逆迁移。
9. 稳定两个发布周期后，才考虑停止写入旧字段；是否删除旧字段另立变更单。

## 11. 分阶段实施计划

  下表按 2 名开发人员、1 名产品/教务负责人和兼职测试/运维估算。若课程制度整理和学校规则确认不能及时完成，开发周期应顺延，不应以猜测补齐业务规则。

| 阶段 | 建议周期 | 交付物 | 退出条件 |
|---|---:|---|---|
| 0. 数据安全基线 | 1 周 | 线上资产清单、备份脚本、异地副本、恢复记录、匿名测试库 | 恢复演练通过 |
| 1. 架构与权限底座 | 2–3 周 | 显式迁移、会话体系、权限码/数据范围、审计日志、基础安全头与验证 | 权限矩阵 API 测试通过 |
| 2. IG 贯通与资讯库 | 3 周 | 学年阶段、资格规范、九年级档案/课程/成绩、官方资讯后台 | 九年级完整主流程通过 |
| 3. 选课与教学班 | 2–3 周 | 课程发布、志愿、审核、容量、教学班编组、教师分配 | 从发布到录取可追溯 |
| 4. 排课 MVP | 4–5 周 | 时段/教室/可用性、冲突中心、草稿求解、锁定、差异、发布/回滚 | 实际规模数据硬冲突为零 |
| 5. 信息架构与体验收口 | 2–3 周 | 角色导航、工作台、列表/表单统一、移动端当天视图、可访问性修正 | 关键任务可用性验收通过 |
| 6. UAT 与上线 | 2 周 | 培训、数据校验报告、演练记录、发布与回滚手册 | 学校签字、备份和回滚再验证 |

  总周期约 16–20 周。阶段 2 的资讯整理可与阶段 1 并行，UX 设计可提前验证，但数据库迁移、权限切换和正式课表发布必须依次经过前置闸门。

## 12. 验收标准

### 12.1 课程贯通

- 九年级学生可拥有独立的学年记录、IG 课程、教学班、成绩和任务，升入十年级后历史不被覆盖。
- 同一学生可同时存在不同考试局或不同资格层级的课程，页面不会混淆评分制。
- 每门正式课程能追溯到资格规范版本和官方来源；过期规则不会用于新考季。
- IG 阶段到 A-Level 的方向建议明确标注为校内建议，不伪装成考试局强制规则。

### 12.2 选课排课

- 学生能提交多志愿，查看审核状态；教务能审批、候补、调班和记录例外原因。
- 已发布课表中教师冲突、学生冲突和教室冲突均为 0。
- 教师不可用时间、锁定课节、班级容量和周课时满足率为 100%。
- 任何无法满足的课程必须在冲突中心显示受影响学生和原因。
- 发布前可查看差异，发布后学生和教师只能看到有效版本，管理员能恢复上一版本。

### 12.3 权限安全

- 每个写接口均有允许与拒绝用例；教师不能访问非任教学生，指导老师不能修改非负责学生。
- 学生修改 URL、请求体或对象 ID 不能访问他人数据。
- 停用账号和撤销会话立即生效；浏览器脚本无法读取会话 Cookie。
- 密码、令牌、监护人完整联系方式和敏感附件不进入应用日志。
- 高风险操作均能按操作者、时间、对象和原因查询审计记录。

### 12.4 数据与运维

- 迁移前后学生、有效选课、成绩、考试计划和院校关系数量一致，所有差异有清单。
- 外键检查无新增孤儿记录，数据库完整性检查通过。
- 使用迁移前备份在隔离环境内完成恢复，并在目标 RTO 内恢复服务。
- 上线失败时能通过功能开关或上一构建恢复现有功能，不需要删除新表或覆盖数据库。

## 13. 主要风险与处理

| 风险 | 表现 | 处理 |
|---|---|---|
| 学校课程路径尚未定稿 | 九年级到底是 IG1、加速 IG 还是基础阶段说法不一 | 用可配置阶段；学校在数据导入前签署课程映射表 |
| 考试局规则随年份变化 | 同科目代码、组件或考季可用性变化 | 规则版本化、有效期、官方来源和双人复核 |
| 现有数据语义不一致 | `grade`、课程名、考试局名存在自由文本 | 先生成冲突报告，建立映射表，不自动猜测覆盖 |
| 排课无解 | 教师时间、学生组合和教室资源无法同时满足 | 冲突中心说明最小冲突集合，由学校调整开班/师资/时段 |
| 权限收紧影响日常工作 | 原本能改的数据突然不可改 | 先观察模式记录拒绝，再分角色试点和培训 |
| 自动迁移损伤线上库 | 启动即改表或中途失败 | 显式迁移、事务、副本演练、维护窗口和可恢复快照 |
| 资讯库被误当绝对结论 | 用户忽略年份、科目和地区差异 | 界面强制显示考试局、版本、生效期、检查日期和原文链接 |

## 14. 开工前需要学校确认的业务输入

- 学校九至十二年级的正式阶段名称、每阶段起止学年和升段条件。
- 当前及计划开设的考试局、资格、科目代码、教学周期和考试系列。
- 必修/选修、先修、互斥、最大最小开班人数和退改课期限。
- 每周作息、单双周、节次、连堂规则、教室及设备、教师不可用时间。
- 谁可最终批准选课、谁可发布课表、谁可更正成绩、谁可查看监护人信息。
- 当前线上 `SQLITE_PATH`、服务启动方式、备份位置、域名/HTTPS 和运维责任人。
- 学生与监护人隐私告知、同意、保存期限、离校后归档/删除规则。

## 15. 第一批开发任务

1. 完成线上只读资产核验和数据库恢复演练，冻结未经审查的直接改库操作。
2. 生成现有数据质量报告：届别、学生状态、课程、选课、单元、考季和用户绑定。
3. 由学校填写“年级—阶段—考试局—资格—科目”映射表，并确认首批 IG 科目。
4. 将当前启动迁移拆为有版本号的显式迁移，增加 `schema_migrations` 与预检报告。
5. 建立服务端权限码、数据范围和审计日志，优先修正教师与指导老师权限。
6. 实现 `student_year_records`、资格规范和来源记录，再开放九年级录入。
7. 完成选课和教学班后，使用匿名化真实规模数据验证排课约束，再开发发布流程。

## 16. 自检结论

  本方案保留现有可用架构，没有把一次升级扩张为多租户平台、微服务重写或无依据的换库项目；新增表均对应已经明确出现的课程版本、教学班、选课流程、排课资源、审计和迁移问题。方案也没有以“最小改动”为由回避必要的权限边界、历史版本和恢复能力。真正开工时仍应以线上只读核验和学校课程规则为准，文档中尚未验证的线上配置不得当作既成事实。
