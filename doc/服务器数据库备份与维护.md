# 服务器数据库备份与维护（SQLite）

　　本文与 **[部署指南.md](./部署指南.md)** 第 8 节、**[版本管理与发布流程.md](./版本管理与发布流程.md)** 中「备份/发布检查」互为补充：侧重 **你在服务器上具体怎么做**、**SQLite + WAL 要特别注意什么**，以及 **恢复前如何降低风险**。

　　应用默认数据库路径由环境变量 **`SQLITE_PATH`** 决定；未设置时，进程工作目录下的 **`database.sqlite`** 即为库文件（见 `app/server/db.js`）。部署在 Docker 时，常见做法是挂载 **`/opt/alevelinfo/data/database.sqlite`** 到容器内路径，并在容器环境或宿主机统一设置 **`SQLITE_PATH`** 指向该文件——**备份与恢复时务必以「实际运行中的路径」为准**，不要凭记忆猜路径。

---

## 一、必须先搞清楚的三个事实

### 1.1 单文件 ≠ 随便 `cp` 就一定安全

　　本项目在 `db.js` 中启用了 **SQLite WAL（Write-Ahead Log）** 模式。此时除主文件 **`database.sqlite`** 外，同一目录下还可能出现：

- **`database.sqlite-wal`**
- **`database.sqlite-shm`**

　　若在业务 **高频写入** 时只复制主文件、不同时处理 WAL，有可能得到 **逻辑不一致或损坏的副本**。因此更推荐下面「二」中的 **`sqlite3 .backup`** 或 **`VACUUM INTO`** 方式生成 **独立一致快照**。

### 1.2 备份时应用是否停机

| 方式 | 优点 | 缺点 |
|------|------|------|
| **热备**（`sqlite3 .backup`，服务不停） | 业务不中断 | 需服务器安装 `sqlite3` CLI；大库时略占 I/O |
| **短停备**（`compose stop` / `systemctl stop` 后复制整库目录或三文件） | 实现简单 | 有短暂不可用窗口 |

　　一般轻量教务系统：**每日低峰热备**即可；重大升级前可再加一次 **停服冷备**。

### 1.3 备份文件也是敏感资产

　　库内含 **账号哈希、学生与升学数据**。备份目录权限应 **仅 root 或部署用户可读**，并 **不要** 把备份提交进 Git、不要放在公网可下载目录。异地拷贝请走 **加密通道**（如 `rsync -e ssh`、对象存储私有桶）。

## 二、推荐实现：使用 `sqlite3` 在线备份（热备）

　　在 **Ubuntu** 类系统上安装官方 CLI（包名可能为 `sqlite3`）：

```bash
sudo apt-get update
sudo apt-get install -y sqlite3
```

　　假设线上库绝对路径为 **`/opt/alevelinfo/data/database.sqlite`**，备份目录为 **`/opt/alevelinfo/backup/`**（需事先 `mkdir -p`）：

```bash
mkdir -p /opt/alevelinfo/backup
sqlite3 "/opt/alevelinfo/data/database.sqlite" \
  ".backup '/opt/alevelinfo/backup/database.sqlite.$(date +%F_%H%M).bak'"
```

　　说明：`.backup` 会在库仍被 Node 打开时生成 **一致快照**（对 WAL 友好）。若命令报错，先 `ls -la` 确认路径与权限。

　　**轮转（示例：只保留最近 14 个按日期命名的备份）** 可在同一脚本末尾追加：

```bash
cd /opt/alevelinfo/backup && ls -1t database.sqlite.*.bak 2>/dev/null | tail -n +15 | xargs -r rm -f
```

## 三、备选实现：停服后整库复制（冷备）

　　与 **部署指南** 中示例一致，适合 **大版本升级前** 或没有安装 `sqlite3` CLI 时。

**Docker Compose 示例：**

```bash
cd /opt/alevelinfo/deploy
docker compose stop
cp -a /opt/alevelinfo/data/database.sqlite "/opt/alevelinfo/backup/database.sqlite.$(date +%F).stop-copy"
# 若目录中存在 -wal / -shm，可一并复制（视你 WAL 文件是否与主文件同目录）
docker compose up -d
```

**systemd 直跑 Node 时：** 对 `alevelinfo.service` 执行 `systemctl stop` 后再 `cp`，逻辑相同。

## 四、定时任务（cron）落地步骤

1. 将 **二** 中命令写入脚本，例如 **`/opt/alevelinfo/scripts/backup-sqlite.sh`**，并 `chmod +x`。  
2. 脚本内写死 **`SQLITE_PATH`** 或通过 **读取与进程相同的环境文件** 取路径，避免换机后静默备错文件。  
3. `crontab -e`（建议用 **部署用户** 而非 root，除非只有 root 能读数据目录）：

```cron
# 每天 03:10 备份（服务器时区）
10 3 * * * /opt/alevelinfo/scripts/backup-sqlite.sh >> /opt/alevelinfo/backup/backup.log 2>&1
```

4. **每月做一次恢复演练**：在测试目录还原一份备份，用 **`sqlite3 … 'PRAGMA integrity_check;'`** 校验，避免「有备份但不可用」。

## 五、恢复流程（务必按顺序）

　　与 **部署指南 §8.2** 一致，强调 **覆盖前再备一份当前坏库或旧库**，防止二次损失。

1. **停应用**（Docker：`docker compose down`；systemd：`systemctl stop …`）。  
2. **把当前 `database.sqlite` 复制一份** 为 `database.sqlite.before-restore.日期`。  
3. 将选定备份复制为运行路径下的 **`database.sqlite`**（路径与 **`SQLITE_PATH`** 一致）。  
4. **启动应用**，登录抽查：列表、登录、任一写操作。  
5. 若恢复失败：用步骤 2 的 **`before-restore`** 文件换回去再启动，回到可服务状态后再查原因。

## 六、与「发布 / 迁移」相关的注意点

- **发版不等于备份**：`git pull`、重建镜像前，建议 **手动或定时已有一份当日备份**；结构迁移脚本若随版本发布，先在 **备份库副本** 上试跑（见版本管理文档中的习惯）。  
- **`JWT_SECRET` 与数据库无关**：恢复旧库不会恢复旧密钥；若你同时回滚了环境变量，会导致全员重新登录，属预期现象。  
- **不要依赖仓库里的空库**：`app/database.sqlite` 若曾误提交，容易与线上混淆；真实数据只留在服务器与加密备份介质。

## 七、检查清单（建议打印或放进运维笔记）

- [ ] 已确认线上 **`SQLITE_PATH` / 挂载卷** 实际指向的文件路径  
- [ ] 已安装 **`sqlite3`** 或使用 **停服复制** 策略  
- [ ] **cron/systemd timer** 已启用且 `backup.log` 无连续报错  
- [ ] 备份目录 **权限** 正确、**不在 Web 根目录**  
- [ ] **至少每季度** 做过一次 **恢复到临时目录 + integrity_check**  
- [ ] 异地或第二磁盘有一份 **周期同步**（防火、防盗、防单盘损坏）
