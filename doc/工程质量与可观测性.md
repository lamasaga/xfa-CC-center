# 工程质量与可观测性

## 为什么重要

　　当用户量与发布频率不高时，「能跑、能 SSH 上去 tail 日志」往往够用。一旦流量、数据量或协作人数上来，**排障成本**和**发布信心**会最先成为瓶颈：同样一个线上问题，有没有结构化日志、有没有请求关联 ID、有没有错误聚合与告警，处理时间可能差一个数量级。

　　可观测性通常拆成三块：**日志（发生了什么）**、**指标（有多频繁/多慢）**、**链路/追踪（跨服务时谁调谁）**。本项目规模以单体 Node + SQLite 为主，优先落地「低成本、高收益」的几项：结构化 HTTP 日志、慢请求标记、探活与健康检查、进程内粗指标、可选 Sentry、API 冒烟测试。

## 本仓库已落地的能力

| 能力 | 说明 |
|------|------|
| 结构化 HTTP 日志 | 每请求一行 JSON（`ts, level, msg, method, path, status, duration_ms, ip`），便于日志平台解析与检索。 |
| 慢请求 | 耗时超过阈值时 `level=warn`，便于筛「慢查询/慢接口」候选。 |
| `X-Request-Id` | 响应头与 500 错误体中带 `request_id`，便于把用户反馈、网关日志与应用日志对齐。 |
| 探活 | `GET /api/health`：SQLite `SELECT 1`，供负载均衡或容器编排探活。 |
| 进程内指标 | `GET /api/metrics`：累计请求数、按路由聚合（UUID 归一为 `/:uuid`）、慢请求计数等；**进程重启清零**，非 Prometheus 级方案。 |
| 可选 Sentry | 配置 `SENTRY_DSN` 且安装 `@sentry/node` 后上报未捕获异常；未配置则不影响运行。 |
| API 冒烟测试 | `app` 目录执行 `npm run test:api`：健康检查、指标鉴权、种子管理员登录、未知 API 的 JSON 404 等。 |

## 环境变量

| 变量 | 作用 |
|------|------|
| `HTTP_LOG_SLOW_MS` | 慢请求阈值（毫秒），默认 `800`。超过则 HTTP 日志 `level=warn`。 |
| `METRICS_TOKEN` | 设置后，`GET /api/metrics` 需在请求头携带 `X-Metrics-Token: <token>` 或 `Authorization: Bearer <token>`。**未设置时该接口返回 404（disabled），避免误暴露。** |
| `SENTRY_DSN` | Sentry 项目 DSN；为空则不上报。 |
| `SENTRY_ENVIRONMENT` | Sentry 环境名，默认取 `NODE_ENV`。 |
| `SENTRY_TRACES_SAMPLE_RATE` | 性能追踪采样率，默认 `0.05`。 |

## 本地与 CI

- 在 `app` 目录执行：`npm run test:api`。
- 若在 Windows 上升级/切换 Node 版本后出现 `better-sqlite3` 的 `NODE_MODULE_VERSION` 不匹配，在 `app` 目录执行：`npm rebuild better-sqlite3` 后再跑测试。
- 建议在 CI（或合并前脚本）中固定 Node 版本并执行 `npm run test:api`，避免「本机能跑、流水线不能跑」的漂移。

## 运维与安全建议

- **`/api/health`**：可给负载均衡做 HTTP 探活；若未来数据库与 Web 进程分离，需评估「只验进程」与「验到 DB」的取舍。
- **`/api/metrics`**：务必配置足够长的随机 `METRICS_TOKEN`；**不要**在无网关鉴权的情况下把整个指标端点暴露到公网。更稳妥的做法是仅内网或 SSH 隧道访问。
- **日志收集**：将应用 stdout 接到 systemd journal、Docker logging driver 或集中式日志服务后，可按 `path`、`status`、`duration_ms`、`request_id` 建检索与简单仪表盘。
- **后续可增强（非必须）**：少量 Playwright E2E、OpenAPI 契约测试、真正的 Prometheus `/metrics` exporter、数据库层慢 SQL 统计（SQLite 场景可结合备份与离线分析）。
